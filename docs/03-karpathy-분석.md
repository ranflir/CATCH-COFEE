# 03. Karpathy 가이드라인 기반 기획 분석

> `/karpathy-guidelines` 적용 — 기획 내용을 **가정/모호함/리스크/단순화** 관점에서 분석. 코딩 전 사고.

## 1. Think Before Coding — 숨은 가정 & 모호함

기획서/기능명세서에서 **조용히 넘어가면 안 되는 가정**들:

| # | 가정/모호함 | 왜 문제인가 | 결정 필요 |
|---|---|---|---|
| A1 | "최적 결제수단 추천"이 **정확한 할인 데이터**를 전제 | 카드사/페이 혜택은 수시 변경·조건 복잡(전월실적/한도/중복불가). 데이터 부정확하면 **추천 신뢰 붕괴** = 핵심 가치 훼손 | 혜택 데이터 소스/갱신 주체를 누구로? 수동 큐레이션 vs 크롤링 vs 제휴 |
| A2 | 크롤링으로 "핵심만 요약" | 비정형 텍스트(SNS/이미지 배너) 파싱은 난도 높음. 명세는 NLP를 가볍게 언급 | V1.0 크롤링 대상을 **정형 데이터가 있는 1~2개 브랜드**로 한정? |
| A3 | "3명 확인 시 자동 등록" | 어뷰징(다계정/담합) 시 허위 정보 자동 노출 | 신뢰도 점수·동일 IP/기기 제한·신고 기반 사후 철회 필요 |
| A4 | "영수증/사진 필수" | 영수증 진위 검증 안 하면 첨부는 형식적. OCR 검증할지? | V1.0은 *첨부만 강제*, OCR 검증은 후순위로? |
| A5 | 결제수단별 "예상 할인액 원 단위 표시" | 메뉴 가격 데이터가 있어야 금액 계산 가능. 메뉴/가격 DB 출처 불명 | 가격 입력 주체(판매자/크롤링/사용자)? 없으면 "할인율"만 표시 |
| A6 | "간편결제 바로 연동(기능5)" | 네이버페이/카카오페이 직접 연동은 **사업자 심사·계약** 필요. 개인/MVP 단계 불가 | V1.0 제외 합의 (아래 단순화) |
| A7 | 위치 권한 미동의 사용자 | 기획서엔 "지명 검색 대체경로" 언급, 명세엔 약함 | 대체 경로 V1.0 포함 여부 |

## 2. Simplicity First — V1.0에서 빼야 할 것 (YAGNI)

CLAUDE.md "V1.1+ 기능 미리 만들지 마"와 동일 철학. **기능명세 중요도 + 외부 의존도**로 컷:

**V1.0 (MVP) 포함:**
- 위치 기반 카페 탐색 + 지도/목록 (기능1)
- 카페 상세 + 출처별 할인 표시 (기능1.3)
- 사용자 제보 + "이 정보 맞아요" + 3인 자동등록 + 검수 (기능6) ← 핵심 차별점
- 판매자 직접 할인 등록 (기능7)
- 최적 결제수단 **추천(표시만)** (기능3) — 실제 결제 X

**V1.1+로 연기 (권장):**
- 🔸 **간편 결제 실제 연동(기능5)** — PG 계약/심사 필요, 명세 중요도=낮음. *추천까지만 V1.0.*
- 🔸 **자동 크롤링 전체(기능2)** — 법적/기술 난도 높음. V1.0은 **판매자 등록 + 사용자 제보**로 데이터 확보, 크롤링은 1개 브랜드 PoC만.
- 🔸 **NLP 자동 추출(2.2.2)** — 규칙 기반 파싱으로 시작, NLP/LLM은 후순위.
- 🔸 **결제수단 기반 알림(4.2)** — 즐겨찾기 알림(4.1)부터.
- 🔸 **OCR 영수증 검증** — 첨부 강제만.

→ 이렇게 컷하면 **외부 계약 의존 0**으로 MVP 출시 가능. 데이터는 판매자+제보로 부트스트랩.

## 3. 데이터 신뢰도 — 이 서비스의 진짜 리스크

핵심 가치 = **"정보가 맞다"**. 기획서 리스크 표도 이를 지목. 설계에 반드시 반영:

- **자동등록 어뷰징 방지**: 확인은 서로 다른 사용자 + (기기/계정 신뢰도) 검증. 자동등록 후에도 신고 시 즉시 비공개.
- **신선도 표기**: 모든 할인에 "정보 갱신일자" + 출처 배지.
- **추천 오류 대비**: 추천 화면에 "정보가 다를 수 있어요/신고" 채널 상시.
- **교차 검증**: 동일 카페에 크롤링 vs 제보 vs 판매자 값 충돌 시 우선순위 규칙(판매자 > 자동등록 제보 > 크롤링?) 정의 필요.

## 4. Goal-Driven — 검증 가능한 성공 기준

모호한 "잘 동작" 대신:

| 기능 | 성공 기준(테스트) |
|---|---|
| 반경 검색 | 좌표+반경 입력 → 반경 내 카페만 반환(경계값 50m/5km 테스트) |
| 3인 자동등록 | 서로 다른 3 user 확인 → status=자동등록 전환 / 동일 user 2회 → 거부 |
| 확인 취소 | 자동등록 전 취소 성공 / 자동등록 후 취소 거부 |
| 추천 | 보유 수단 N개 × 할인 → 최대 할인 수단 1개 + 예상액(또는 할인율) 반환 |
| 판매자 할인 검증 | 할인율 0~100% 밖 / 종료<시작 → 거부 |
| 제보 첨부 | 이미지 없는 최초 제보 → 거부 |

## 5. Surgical / 결론

- **결정 1순위**: V1.0 범위 확정(위 §2). 이것이 스택·일정·외부연동 전부를 좌우.
- **결정 2순위**: 메뉴/가격 데이터 출처(A5) — 추천 금액 표시 가능 여부 결정.
- **결정 3순위**: 크롤링 합법성·범위(A2, A6).

이 3개가 정해지면 나머지(스키마/엔드포인트/연동)는 기계적으로 진행 가능.
