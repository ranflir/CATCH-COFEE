# 02. 기술 스택 / 구조 설계

> `/brainstorming` 결과. 본 문서는 **검토용 제안**이며, 사용자 확정 후 README와 함께 고정한다.

## 0. 설계 제약 / 입력

- **역할 3종**(User/Seller/Admin) + **디바이스 2종**(모바일 앱 iOS/Android, 반응형 웹).
- **크롤링 워커**(스케줄 + 파싱 + 검수 큐)가 독립적으로 돌아야 함.
- **결제(PG) 연동**, **푸시 알림**, **지도/장소 검색**, **이미지 업로드** 등 외부 연동 다수.
- 사용자의 기존 프로젝트(WARA)가 **pnpm + Turborepo 모노레포 / NestJS / Next.js / Expo / Drizzle + PostgreSQL**. → 컨벤션 일치 시 학습비용·재사용 이득 큼.

## 1. 아키텍처 옵션 비교

### 옵션 A — 모노레포 + NestJS (권장)
WARA와 동일 구조. `apps/api`(NestJS) + `apps/web`(Next.js) + `apps/mobile`(Expo) + `apps/crawler`(워커) + 공유 `packages`.

- **장점**: 역할/디바이스가 많은 이 서비스에 맞는 명확한 레이어 분리. 크롤링 워커 독립 배포. 타입·DTO 패키지 공유. **WARA 컨벤션 그대로** → 스킬(`api-design`=NestJS, `drizzle-schema`) 즉시 활용.
- **단점**: 초기 셋업·인프라 구성요소(서버+워커+Redis)가 가장 많음. MVP까지 시간 ↑.

### 옵션 B — Next.js 풀스택 (MVP 속도 우선)
`apps/web`(Next.js, Route Handlers로 API 겸용) + `apps/mobile`(Expo) + `apps/crawler`(독립 워커). NestJS 제거.

- **장점**: 백엔드 서버 1개 줄어 셋업·배포 단순. 웹 우선 MVP를 가장 빠르게.
- **단점**: 도메인 로직이 Next 안에 섞임 → 역할/권한·결제·검수 흐름 복잡해지면 경계 흐려짐. 모바일 앱이 Next API에 의존(서버리스 함수 cold start, 장시간 작업 부적합).

### 옵션 C — BaaS(Supabase) + Next/Expo (가장 빠름)
Supabase(Postgres+Auth+Storage+Edge Functions) + Next.js + Expo. 크롤러만 별도.

- **장점**: Auth·Storage·DB·실시간을 한 번에. 가장 빠른 프로토타이핑. 영수증 이미지 Storage 기본 제공.
- **단점**: 벤더 종속, 복잡한 추천/검수 로직은 Edge Function 한계. Drizzle 직접 운영 대비 제어력 ↓. WARA 컨벤션과 이탈.

### 추천: **옵션 A**
이 서비스는 *역할 3종 × 출처 3종 × 검수/자동등록 상태기계 × 크롤링 워커 × 결제*로 도메인 복잡도가 충분히 높다. Next 풀스택(B)은 이 복잡도에서 경계가 무너지기 쉽고, BaaS(C)는 추천·검수 로직 제어가 약하다. WARA와 동일 스택이라 **재사용·일관성 이득이 결정적**.
다만 **MVP를 최대한 빨리** 원하면 옵션 B로 시작 후 백엔드만 NestJS로 분리하는 단계적 전환도 가능 — 이 결정은 사용자 확인 필요.

## 2. 권장 스택 상세 (옵션 A 기준)

| 레이어 | 기술 | 비고 |
|---|---|---|
| 모노레포/빌드 | pnpm 10 + Turborepo | WARA 동일 |
| 언어 | TypeScript (strict, `any` 금지) | CLAUDE.md 규칙 |
| API 서버 | **NestJS** | `api-design` 스킬 |
| ORM/DB | **Drizzle ORM + PostgreSQL** | raw SQL 금지, migration 필수 |
| 공간 검색 | PostgreSQL + **PostGIS** (또는 위경도 + `earthdistance`) | 반경 50m~5km 쿼리 |
| 웹 | **Next.js** (App Router) | 사용자/판매자/관리자 |
| 모바일 | **Expo (React Native)** | iOS/Android, Expo Notifications |
| 캐시/큐 | **Redis** + BullMQ | 크롤링 잡 큐, 추천 캐시 |
| 크롤링 | Node + **Playwright**(동적) / **Cheerio**(정적) | 워커(`apps/crawler`) |
| 인증 | JWT (access+refresh) + bcrypt | 평문 금지 |
| 검증 | **Zod** | DTO 검증 (`api-design` 스킬) |
| 스토리지 | S3 호환(예: Cloudflare R2) | 영수증/사진 |
| 푸시 | FCM (Expo Push) | 4번 기능 |
| 로깅 | 구조화 logger (pino 등) | console.log 금지 |
| 컨테이너 | docker-compose (PG, Redis) | 로컬 개발 |

## 3. 권장 디렉터리 구조

```
catch-coffee/
├─ apps/
│  ├─ api/                # NestJS — REST API, 인증, 추천, 검수 로직
│  │  └─ src/modules/{auth,cafes,discounts,reports,payments,recommendations,notifications,seller,admin}
│  ├─ web/                # Next.js — user/seller/admin (route group 분리)
│  ├─ mobile/             # Expo — user 앱
│  └─ crawler/            # 크롤링 + 파싱 + 스케줄러 워커
├─ packages/
│  ├─ db/                 # Drizzle schema + migrations (단일 소스)
│  ├─ types/              # 공유 DTO/Zod 스키마
│  ├─ ui/                 # 공유 UI 컴포넌트
│  ├─ tsconfig/
│  └─ eslint-config/
├─ docker-compose.yml     # postgres, redis
└─ docs/
```

## 4. 데이터 모델 핵심 엔터티 (초안)

> 상세 스키마는 확정 후 `drizzle-schema` 스킬로 별도 설계.

- `users` (role: user/seller/admin, 신뢰도 점수)
- `cafes` (브랜드, 지점, 위경도/PostGIS point, 주소, 영업시간)
- `discounts` (cafe_id, 출처 enum[crawl|seller|report], 정률/정액, 기간, 조건JSON, 상태, payment_method 조건)
- `discount_reports` (제보: cafe_id, 작성자, 입력값, 영수증 image_url, 상태[대기/검수중/승인/반려/자동등록])
- `report_confirmations` (제보 확인: report_id, user_id) — **(report_id, user_id) unique** = 1인 1회
- `payment_methods` (user_id, 종류, 암호화 토큰, 기본여부)
- `favorites` (user_id, cafe_id)
- `notification_settings` / `notifications`
- `crawl_jobs` / `crawl_logs` (실행 로그, 실패 추적)
- 공통: soft delete(`deleted_at`), `created_at/updated_at`

## 5. 핵심 비기능 결정

- **멱등성**: 제보 등록·확인·결제 요청에 Idempotency-Key.
- **Soft delete** 우선(hard delete 금지).
- **DB 변경 시 migration 필수**.
- **Verify 게이트**: `pnpm lint && typecheck && test && build`.
